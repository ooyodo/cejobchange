# BTCONJP 2026 スライド図解設計

> セッション「『棚卸しお願いします』を減らすために」の図解方針。
> GitHub上（PRの画面）でMermaid図がレンダリングされます。

---

## 結論：単一フレームワークより「視覚言語の統一」

このセッションの主張は **「人がやっていた部分を、質を落とさずに仕組みへ移し続けている」** です。
つまり話の全編を貫くのは *人と仕組みの境界線が動いていく* という一本の軸。

そこで、フレームワークを1つ選ぶより **全図を通して色の意味を固定する** ほうが効きます。

| 色 | 意味 | 用途 |
|---|---|---|
| 🟠 オレンジ | **人**がやっている | As-Isで支配的。減っていくほど話が進む |
| 🔵 ブルー | **仕組み**がやっている | 増えていく |
| ⚪ グレー | 未着手・これから | レアケース、今後の課題 |
| 🔴 レッド | 事業都合による**例外** | OS固定、長期保管など |

この4色を全スライドで統一すると、聴衆は**凡例を1回覚えるだけで、以降どの図も色だけで読める**ようになります。
「オレンジが減ってブルーが増える」という画の変化そのものが、このセッションのストーリーになります。

## 1. WBS（作業分解構成図）× 人／仕組みの色分け ★中核

ご質問の作業分解構成図を当てはめると、こうなります。
**ポイントは、WBSを"作業の一覧"としてではなく"色を塗る土台"として使うこと。**
同じWBSを3回見せ、色だけを変えることで変遷を語ります。

### 1-A. As-Is（プロジェクト任せだった頃）

```mermaid
flowchart TD
    R([デバイス棚卸し運用]):::root

    R --> W1[1 台帳を正しく保つ]:::mid
    R --> W2[2 ズレを是正する]:::mid
    R --> W3[3 ライフサイクルを回す]:::mid
    R --> W4[4 例外に対応する]:::mid

    W1 --> W11[1.1 端末情報の登録]:::human
    W1 --> W12[1.2 台帳とMDMの突合]:::human
    W1 --> W13[1.3 差分の検知]:::human

    W2 --> W21[2.1 所有者への確認]:::human
    W2 --> W22[2.2 管理者への催促]:::human
    W2 --> W23[2.3 現物の所在確認]:::human
    W2 --> W24[2.4 回収・返却]:::human

    W3 --> W31[3.1 調達・キッティング]:::human
    W3 --> W32[3.2 貸与]:::human
    W3 --> W33[3.3 保管]:::human
    W3 --> W34[3.4 回収・廃棄]:::human

    W4 --> W41[4.1 OS固定端末]:::human
    W4 --> W42[4.2 BYOD]:::human
    W4 --> W43[4.3 レアケース]:::none

    classDef root fill:#2C3E50,stroke:#1B2631,color:#ffffff
    classDef mid fill:#EAECEE,stroke:#85929E,color:#1a1a1a
```

→ **ほぼ全部オレンジ。** 「各プロジェクトの善意と手作業で支えていた」が一目で伝わります。

### 1-B. 現在（突合と催促を仕組みへ移した後）

```mermaid
flowchart TD
    R([デバイス棚卸し運用]):::root

    R --> W1[1 台帳を正しく保つ]:::mid
    R --> W2[2 ズレを是正する]:::mid
    R --> W3[3 ライフサイクルを回す]:::mid
    R --> W4[4 例外に対応する]:::mid

    W1 --> W11[1.1 端末情報の登録<br/>申請不要化]:::system
    W1 --> W12[1.2 台帳とMDMの突合]:::system
    W1 --> W13[1.3 差分の検知]:::system

    W2 --> W21[2.1 所有者への通知]:::system
    W2 --> W22[2.2 管理者へエスカレーション]:::system
    W2 --> W23[2.3 現物の所在確認]:::human
    W2 --> W24[2.4 回収・返却]:::human

    W3 --> W31[3.1 調達・キッティング]:::human
    W3 --> W32[3.2 貸与]:::human
    W3 --> W33[3.3 保管]:::except
    W3 --> W34[3.4 回収・廃棄]:::human

    W4 --> W41[4.1 OS固定端末]:::except
    W4 --> W42[4.2 BYOD<br/>30日で自動整理]:::system
    W4 --> W43[4.3 レアケース]:::none

    classDef root fill:#2C3E50,stroke:#1B2631,color:#ffffff
    classDef mid fill:#EAECEE,stroke:#85929E,color:#1a1a1a
    classDef human fill:#F6C177,stroke:#9A6A1F,color:#1a1a1a
    classDef system fill:#7FB3D5,stroke:#1F618D,color:#1a1a1a
    classDef none fill:#D5D8DC,stroke:#7B7D7D,color:#1a1a1a
    classDef except fill:#F1948A,stroke:#943126,color:#1a1a1a
```

→ **「気づく」側（1.x・2.1・2.2）が青くなり、「直す」側（2.3・2.4）はオレンジのまま。**
これがセッションの核である *線引き* をそのまま可視化した図になります。言葉で説明するより速い。

→ 赤い2つ（保管・OS固定端末）が柱6につながる伏線になります。

### 1-C. これから（M&A後のスケール要件）

同じWBSに「M&Aで増える組織」の軸を掛けて、
どのワークパッケージがスケールしないかをグレーに塗り直す版を用意すると、柱7の締めになります。

> ⚠️ **要確認**: 上記の色分けはこれまでの会話から推定したものです。特に 3.x（ライフサイクル）と 4.1（OS固定端末）の
> 現状が人手なのか一部仕組み化済みなのか、実態に合わせて塗り直してください。

## 2. 状態遷移図：閾値とエスカレーション ★柱4の山場

90日・180日の設計は本質的に**ステートマシン**なので、状態遷移図が最適です。
表で日数を並べるより、状態と遷移条件で見せるほうが「設計している感」が出ます。

```mermaid
stateDiagram-v2
    [*] --> 正常: 登録（申請不要）
    正常 --> 要確認: 90日チェックインなし
    要確認 --> 正常: チェックイン再開
    要確認 --> 紛失リスク: さらに放置（180日）
    紛失リスク --> 正常: 所在確認・返却
    紛失リスク --> [*]: 回収・廃棄

    note right of 要確認
        所有者へ通知
    end note
    note right of 紛失リスク
        管理者へ
        パブリックにエスカレーション
    end note
```

### BYODは別のステートマシン

```mermaid
stateDiagram-v2
    [*] --> 登録済: 申請不要で登録
    登録済 --> 削除: 30日チェックインなし
    削除 --> 登録済: いつでも再登録（申請不要）
```

→ 「締め付けるのではなく、出入り自由にして放置分だけ整理する」という発想が図で伝わります。

### 応用：この図の"穴"を見せる ★柱6への橋渡し

```mermaid
stateDiagram-v2
    [*] --> 正常
    正常 --> 要確認: 90日チェックインなし
    要確認 --> 紛失リスク: 180日チェックインなし
    正常 --> 預かり中: 情シスが保管（通電なし）
    預かり中 --> 正常: 検証で持ち出し

    note right of 預かり中
        チェックインなし = 行方不明
        とは限らない
        iOSはMDMプロファイルが
        期限切れになることも
    end note
```

→ **「単純な日数では割り切れない」という論点を、前の図との差分で示せます。**
同じ図に状態を1つ足すだけなので、聴衆が理解を積み上げやすい構成です。

## 3. 象限図：自動化の線引きの判断基準 ★柱5

「どこまでを仕組みに任せるか」は言葉で説明すると抽象的になりがちなので、2軸に落とします。

```mermaid
quadrantChart
    title 何を仕組みに任せ、何を人に残すか
    x-axis 判断が単純 --> 判断が複雑
    y-axis 発生頻度が低い --> 発生頻度が高い
    quadrant-1 仕組みが提示し人が判断
    quadrant-2 仕組みに任せる
    quadrant-3 後回しでよい
    quadrant-4 人がやる
    "台帳とMDMの突合": [0.15, 0.85]
    "所有者への通知": [0.2, 0.75]
    "エスカレーション": [0.35, 0.6]
    "現物の所在確認": [0.8, 0.45]
    "OS固定端末の扱い": [0.9, 0.3]
    "レアケース対応": [0.7, 0.12]
```

→ 「頻度が高くて判断が単純なものから仕組みへ寄せた」という着手順の合理性が一目で伝わります。
→ **プロットの位置は仮置き**です。実感に合わせて動かしてください。

## 4. ライフサイクル図：ポリシーで決めるべき分岐 ★柱2

「ポリシーの言語化が先」という主張は、**どこに判断ポイントがあるかを示す図**とセットにすると効きます。

```mermaid
flowchart LR
    P1[調達]:::step --> P2[キッティング]:::step --> P3[貸与]:::step
    P3 --> P4[利用・検証]:::step
    P4 --> P5[保管]:::except
    P5 --> P4
    P4 --> P6[回収]:::step
    P6 --> P7[廃棄 / 再貸与]:::step
    P7 -.-> P3

    classDef step fill:#EAECEE,stroke:#85929E,color:#1a1a1a
    classDef except fill:#F1948A,stroke:#943126,color:#1a1a1a
```

→ 各ノードに「ここで何を決めておくべきか」を吹き出しで足していくと、柱2が図だけで進行できます。
→ 保管（赤）だけがループを持つ＝ここが厄介、という構造も同時に示せます。

## 5. 対立構造図：セキュリティの定石 vs 事業の現実 ★柱6の前半

OS固定の話は、対立を対立として描くのがいちばん伝わります。

```mermaid
flowchart LR
    subgraph L[管理側の定石]
        direction TB
        A1[最新OSへ更新したい]
        A2[MDMサポート内に統一したい]
        A3[脆弱性を残したくない]
    end

    subgraph R[事業側の現実]
        direction TB
        B1[顧客は様々なOSで遊んでいる]
        B2[旧OSの顧客にも売上がある]
        B3[実機での動作検証が必要]
    end

    L <==>|どこで折り合うか| R

    style L fill:#D6EAF8,stroke:#1F618D
    style R fill:#FADBD8,stroke:#943126
```

→ 「正解が一つに決まらない」ことを図の形（左右対称・矢印が双方向）で表現できます。
→ ここは**answerを出さずに問いのまま置く**のが誠実で、かつ議論を呼びます。

## 6. タイムライン：変遷と現在地 ★柱1・柱7

```mermaid
timeline

    プロジェクト任せ : 各PJに管理者を立てて依頼 : 負担は分散するが積み上がらない
```

→ 冒頭（柱1）でグレーアウトした状態で見せ、終盤（柱7）で全部点灯させると、話の一貫性が出ます。

## 7. カバレッジ図：広い範囲から埋めていく ★柱4

Mermaidでは同心円が描けないため、これはスライドツールで作図してください。構造だけ示します。

```
        ┌─────────────────────────┐
        │  ④ 人が動かない場合      │  ← まだ埋めている最中
        │  ┌───────────────────┐  │
        │  │ ③ レアケース        │  │
        │  │  ┌─────────────┐   │  │
        │  │  │ ② 例外あり    │   │  │
        │  │  │ ┌─────────┐ │   │  │
        │  │  │ │① 大多数  │ │   │  │  ← 最初にここを仕組み化
        │  │  │ └─────────┘ │   │  │
        │  │  └─────────────┘   │  │
        │  └───────────────────┘  │
        └─────────────────────────┘
```

→ 内側から順に色が塗られていくアニメーションにすると「広くカバーできるところから」が直感的に伝わります。
→ 一番外側が塗り切れていない＝「まだ途中」という締めにも接続します。

## 図解の使い分けまとめ

| 柱 | 内容 | 推奨フレームワーク | 節 |
|---|---|---|---|
| 1 | As-Is | WBS（オレンジ一色）＋ タイムライン（グレー） | 1-A, 6 |
| 2 | 順番論 | ライフサイクル図 ＋ 判断ポイントの吹き出し | 4 |
| 3 | PCで型を作る | 構成図のBefore/After（横展開できる形への抽象化） | ※要作図 |
| 4 | 検証端末へ広げる | 状態遷移図 ＋ カバレッジ同心円 | 2, 7 |
| 5 | 線引き | WBS（色が変わった版）＋ 象限図 | 1-B, 3 |
| 6 | 検証端末の難所 | 対立構造図 ＋ 状態遷移図の"穴"版 | 5, 2応用 |
| 7 | M&Aと現在地 | タイムライン（全点灯）＋ WBS（スケールしない箇所） | 6, 1-C |

### 作図で気をつけること

- **色の意味は絶対に変えない。** 途中で意味が変わると聴衆は色を読まなくなります
- **1スライド1メッセージ。** WBSのように情報量の多い図は、色だけを変えて複数回出す
- **同じ図を育てる。** 状態遷移図に状態を1つ足す、WBSの色を塗り替える——新しい図を毎回出すより理解が積み上がります
- **凡例は最初に1枚使って明示する。** ここをケチると以降の全図の効きが落ちます
- Mermaidはスライドに貼るには素っ気ないので、**構造検討はMermaidで、清書はスライドツールで**が現実的です
